# 系统评估

评估基于 v0.2.0 当前代码、API、存储、测试和界面链路。分数用于表示工程成熟度，不是产品价值排名。

## 结论

Rhine-Lore 已具备完整且有差异化的内部 Alpha：从 TXT 导入、阅读、百万字分析、视觉分支，到工作台创作、对话提议、版本恢复和 Vault 资料治理，主链路已经贯通。它目前适合单用户本机使用和持续验证，不适合直接开放公网，也还没有达到低维护成本的公开 Beta 工程状态。

**定位建议：继续成为“本地优先的故事操作系统”，而不是通用 AI 聊天器。** 最有价值的闭环是“读懂已有长篇 -> 在任意位置分支 -> 提取为结构化创作数据 -> 对话和编辑继续写”，以及“对话提议 -> 用户确认 -> 快照写入 -> 可恢复”。

## 已验证的强项

- 后端关键测试覆盖项目、演化、书籍导入、分析、分支、工作台、版本和备份。
- 百万字规划不会整体加载全文，章节可延迟读取。
- 长篇分析节点持久化并使用内容哈希缓存，支持暂停/恢复判断。
- 书籍存储有进程内可重入锁；ZIP 恢复校验路径和文件类型。
- SQLite Vault 备份使用事务一致性副本。
- 模型配置读取会屏蔽密钥，完整备份排除模型配置文件。
- Agent 修改既有项目/书籍前可生成快照，恢复前也保存当前状态。
- Android 与 Web 共用产品能力，减少平台功能分叉。

## 主要问题

### P0：发布阻断

1. **网络边界不安全**：无鉴权且 CORS 为 `*`，写接口可被局域网来源调用。
2. **Agent 确认只在客户端**：执行端没有确认 nonce、用户身份或授权上下文。
3. **并发与重复执行**：项目 JSON 写入缺少项目级锁；非幂等接口没有请求幂等键。
4. **接口无稳定契约**：没有 `/v1`、OpenAPI、工具 Schema、统一错误码或能力发现。
5. **前端回归风险**：`App.vue` 与全局样式均超过一万行，页面冲突修复容易影响无关模式。

### P1：质量与规模

1. 长篇任务使用进程内线程，没有持久任务队列、并发配额和资源预算。
2. 实体提取缺少系统化的同名消歧、事实冲突和来源证据展示。
3. 模型工具调用依赖文本 JSON 提取，不如结构化 tool calling 稳定。
4. 后端路由集中在单个大型处理器，输入校验和错误语义分散。
5. 前端缺少组件单测、视觉回归和提交到 CI 的关键流程 E2E。
6. `README`、包元数据和发布文档曾出现版本口径不一致，本轮已统一为 v0.2.0，但仍需要自动检查。

## 发布判断

| 目标 | 判断 |

| 单机内部 Alpha | 可用，建议持续备份 |

## 范围控制

下一阶段不建议优先建设社交社区、团队实时协作、复杂插件市场或通用机器人平台。应先让“导入、读懂、分支、转工作台、继续创作、可恢复”成为稳定、可解释、可测量的一条主链路。
