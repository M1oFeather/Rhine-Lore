# 安全与确认

## 当前威胁模型

Rhine-Lore v0.2.1 按单用户、本机应用设计。当前 HTTP 服务：

- 没有登录、会话、API Token、角色或资源级授权；
- 返回 `Access-Control-Allow-Origin: *`；
- `/lore-api/agent/execute` 只检查工具是否在写入白名单，不验证用户是否真的确认；
- 项目、书籍、备份、模型配置等接口与前端共享同一网络边界。

因此，绑定 `0.0.0.0` 后，同一网络中的恶意页面或进程可能尝试调用写接口。不得将当前服务直接映射到公网，也不要在没有额外认证的反向代理后公开部署。

## 推荐部署

| 场景 | 当前建议 |
| --- | --- |
| 单机桌面/Android | 绑定回环地址或 App 私有本机端口，推荐 |
| 家庭可信局域网 | 可临时使用；启用防火墙并限制网段 |
| 公司共享网络 | 不推荐，除非外层实现强认证与来源限制 |
| 公网、云主机、多用户 | 当前不支持 |

## 确认交互要求

宿主收到 `pending: true` 的动作后，必须：

1. 显示人类可读的动作名称，同时保留原始工具名。
2. 显示目标项目/书籍、目标对象 ID、关键参数和正文变更预览。
3. 对多个动作逐项确认，不提供默认全选。
4. 对删除、合并、重置、整章替换增加二次确认。
5. 执行时使用原始 `args`；任何用户编辑都应形成新的明确参数预览。
6. 成功后显示快照和恢复入口；没有快照时明确告知。
7. 失败后读取当前状态，再决定是否重试。

!!! warning "非幂等操作"
    `create_project`、`import_txt`、所有追加/新增工具和 `evolution_advance` 重复执行会产生额外数据或额外回合。网络超时不能作为自动重试依据。

## 模型与附件

- 在线模型会收到会话消息、系统工具说明和选中的附件片段。
- 附件与 Vault 检索内容都应视为不受信输入，可能包含提示注入文本。
- 当前没有把“资料中的指令”和“用户指令”进行可靠隔离；Agent 不应因为附件要求而绕过确认。
- API Key 只保存在本机模型配置中，配置读取接口会脱敏，备份不会导出密钥。
- `update_llm_config` 故意不接受 API Key；外部 Agent 不应尝试扩展这一能力。

## 接入检查表

- [ ] 服务只绑定在预期接口，未直接暴露公网。
- [ ] 宿主对所有写工具实现明确确认。
- [ ] 删除和结构变更实现二次确认。
- [ ] 日志不记录 API Key、完整私密附件或不必要的正文。
- [ ] 执行响应中的快照可被用户找到并恢复。
- [ ] 超时后先读取状态，不自动重放写请求。
- [ ] 外部内容不能修改宿主的确认策略。
- [ ] 备份文件保存在受控位置，导入前验证来源。

## 发布前必须补齐

1. 本机会话或 Bearer Token，并让所有 Lore 写接口统一验证。
2. 精确的 Origin 允许列表，默认只允许应用自身来源。
3. 服务端签发、短时有效、绑定工具与参数哈希的确认 nonce。
4. `Idempotency-Key` 与执行结果记录，保护非幂等写入。
5. 每个工具的 JSON Schema、字段长度限制和严格类型校验。
6. 结构化审计日志，记录主体、动作、目标、确认、快照与结果，但不记录密钥。
7. 项目级写锁与冲突检测。

在这些能力完成前，Agent API 的正确定位是“受信本机产品接口”，不是开放平台 API。
